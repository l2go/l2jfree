The tick · Part 1

One thread owns the blow

L2JFree 3.3.1 runs the tasks of the world on one thread: movement, visibility, effects, AI, combat and the logic of client packets. Periodic saves moved off that thread, but many writes made by a player's actions did not, and while one of them waits, the world waits. A few threads outside the world still change creatures, and this release does not fix that.

25 November 2026 · 8 min read

In Lineage II, an online role-playing game, a player attacks a monster that is running away. The attack does not take the monster's health at once. It schedules a hit for the moment the swing lands, and the monster keeps moving in between. When the hit comes due, it changes the health of a creature whose position and list of neighbors other tasks keep changing. This note is about who is allowed to make that change, and what the answer costs.

The problem

Until 3.3.1 the answer was: any thread that happened to pick the task up. The server had two pools of platform threads, which are ordinary operating-system threads. A scheduler pool ran timed work, and an instant pool ran for work that should start at once, the logic of client packets among it. With eight processors visible to the JVM, the default options gave 34 threads, 23 in the first pool and 11 in the second. The hit, the monster's next step, its regeneration and a packet from the player could all run at the same moment, each on a thread of its own.

Health shows what that meant. A blow read the target's health, subtracted the damage and wrote the result back. A regeneration tick did the same with an addition. The write held a monitor (a Java lock on an object, here the creature's status); the read before it did not. Two blows on two threads could read the same health, and the second write would erase the first. A regeneration tick could write back health that a blow had just taken. Nothing would fail and nothing would be logged; the damage of one blow would simply be gone. A unit test that runs on one thread cannot show this kind of defect.

The old code had monitors on a player here and on an item there. Each made one place safe against the cases someone had thought of, and none of them stated the rule.

3.3.1 states it: one thread runs the tasks of the world.

The decision

World tasks share one platform thread, l2jfree-world. Movement, the update of a creature's knownlist (the objects it can see), effects, AI, regeneration, the timed hit and the logic of a client packet are tasks on it. A task queued from that thread runs after the current one returns, not beside it. In the opening scene, the hit waits for a movement step that is running, and the next step waits for the hit.

The health code did not change. It is safe now because a blow and a regeneration tick no longer meet: one of them finishes before the other starts.

The rule has a boundary, and in 3.3.1 it has holes. It covers the tasks of the world; writing a packet to the socket is a separate step on an I/O thread. Some threads outside the world still change creatures directly. That is a defect of this release, not part of the design, and Known defects in 3.3.1 names the known cases.

Steps from other threads

A step that must run on the world thread but starts elsewhere is handed over with runOnWorld. A caller on another thread waits for the step and gets back the failure it threw; a call made from the world thread runs at once, nested in the current task.

Some systems keep threads of their own. The Dimensional Rift hands the steps of both its timers to the world thread this way, and a Seven Signs Festival step that touches the world moves across the same way. An Olympiad game thread hands over only the blocks it wraps in onWorld; the rest of it is one of the holes. A GM (game master) command arrives as a client packet on the world thread, moves to a virtual thread and comes back through runOnWorld whole, with any database wait inside it. The virtual thread only waits and keeps time.

Two shapes not taken

Keeping the pools and putting a lock on each creature would close the race on health. But one blow can write two creatures: damage reflected back changes the attacker in the same step as the target. Such a step would take two locks, and every such step would have to take them in the same order, or two steps could wait for each other forever. The item write in Known defects in 3.3.1 shows that trap on a single object. Cutting the map into regions, a thread each, would trade the cost of one thread for the cost of agreeing at the borders whenever a chase or a fight crosses one. Neither cost was measured. These are the reasons one thread came first.

Work that leaves the world thread

One slow query on the world thread holds every player. So 3.3.1 moves some waits to virtual threads, Java threads that are cheap to park while they wait. These are the waits of the item flush, the save of dropped items, the stored game clock, the global tasks and the character load. A periodic job runs one at a time; a tick that finds the previous run still going is skipped.

Work that leaves the world must not read the world while it is away. The autosave shows the pattern. In 3.3.0 it ran the whole save on a scheduler thread and read the player while other threads changed it. Now it copies the player on the world thread: the character row, the subclasses, the cooldowns and the effects. A virtual thread writes the copy. The copy is not everything the write touches: a summoned pet is still read live, and so is the player's inventory when UpdateItemsOnCharStore is on, which it is not by default.

Someone also has to decide whether a late result still counts. Each autosave copy carries a generation number, and a copy that a newer one has overtaken is not written. The save at logout claims the row: it waits for a write already in progress and refuses any copy still waiting behind it. A character load has one owner; a disconnect or a newer selection takes ownership away, and a load that has lost it does not enter the world. An item write keeps two facts apart: whether the item's row exists, which follows the INSERT or the DELETE, and whether the row still matches memory, which holds only if the item did not change during the SQL. So an item that changed during its own insert is updated next time, not inserted twice.

What it cost

One worker's throughput. A task that runs long delays every task behind it. A world task or a client packet that runs longer than five seconds is logged when it returns; one that never returns is never logged. Work on virtual threads and steps handed over with runOnWorld are not logged at all. An admin command that runs that long tells the GM. There has been no load measurement, and 3.3.1 does not claim a number of players.

Many database writes still wait on the world thread. Only the jobs above moved. Logout's save, the commit of a multisell exchange (a trade of items for items at an NPC), an admin command and the creation of a character wait for the database on the world thread. So do everyday actions such as learning a skill, registering a shortcut or saving a macro. While such a call waits, no other world task runs. Logout's save can also wait for an autosave of the same player that is already writing.

Two options are gone. BaseThreadPoolSize and ExtraThreadPerCore are no longer read; a file that still names them is not an error.

Known defects in 3.3.1

The release shipped with these defects, and none of them is fixed in it. The autosave's pet read and the unordered item write were known and written down when it shipped. The other threads were found by reading the code, not by a test or by a report from a running server. The list is not a complete audit.

Threads that touch creatures without handing the step over. In each case below, a thread outside the world reads or changes a creature while world tasks may be changing it, which is the race this release set out to remove.

  • An Olympiad game thread writes a player's stadium id, closes and opens the stadium doors (a door is a creature too) and sends packets outside its onWorld blocks.
  • When an account logs in while its character is still in the world, the login module kicks the character from its own thread, and the disconnect removes it from the world there.
  • The Monday raid points reset runs as a global task on a virtual thread. When it lifts a clan's reputation to zero or above, the clan's skills are restored to its online members from that thread.
  • The telnet console, off by default, runs on a thread of its own and from there kicks players, gives them items and sends them to jail.
  • The autosave reads a summoned pet on a virtual thread while the world changes it.

An item write that is not ordered. An ordinary item write takes a lock that orders the writes of one item. A caller that already holds the item's monitor cannot wait for that lock: a writer holds the lock while it needs the monitor to record its result, and the two would wait for each other. Such a caller writes around the lock, so its write is not ordered against a background write of the same item that is already in its SQL. 3.3.1 has no lock for the item's state that would close the gap.

How it is verified

ThreadPoolManagerTest checks that world tasks share one platform thread, recognized by identity rather than by name. WorldBoundaryTest works on test operations. It checks the handover (the failure reaches the caller; a closed world or an interrupt does not leave the caller waiting), that a step on the world thread is not split by another task, and the copy-then-write mechanism the autosave uses, though not the autosave itself. CharacterLoadTest checks that a newer selection or a disconnect takes the load from its owner. ItemWriteRacePostgresTest runs against PostgreSQL 18, not a mock, and checks that an item changed during its insert is not inserted twice and that an older write does not replace a newer one.

In CI, a smoke test takes 24 scripted clients, six at a time, through login, character creation, entry into the world and logout, on amd64 and on arm64. Both architectures passed on the release commit. That checks the sequence under some concurrency; it is not a load test.

Not verified: a recording of one fight showing that the position update, the knownlist update, the effect and the hit all ran on the same thread. It was planned as the acceptance check for this step and has not been made. Nothing here measures how many players one world thread carries, and no test covers the defects named above.

The monster's health now changes on one thread, one blow at a time. The same thread works out who should hear about it. The next note follows the packet from that decision to the players nearby, including one packet that reached the socket after its player had left.

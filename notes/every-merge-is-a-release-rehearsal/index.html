Reviving L2JFree · Part 4

Every merge is a release rehearsal

Both architectures check client sessions, restart, shutdown, and restore. Updates from edge are rehearsed when it is available; a versioned release requires completed update proofs. A separate amd64 job checks an empty catalog and a missing catalog directory.

30 October 2026 · 8 min read · revised 15 November 2026

Unit tests check local decisions. An operator also needs to know whether the delivered image admits a player and preserves accounts and characters across a restart, a restore, and an image replacement. L2JFree 3.3.0 records those deployment checks in build.yml.

The jobs and their boundaries

The image-platform matrix runs on native ubuntu-24.04 and ubuntu-24.04-arm runners for amd64 and arm64. It waits for the build, PostgreSQL integration tests, and Jython syntax checks. Each architecture builds from the verified distribution and runs its own rehearsal. An architecture whose checks fail cannot publish its digest. The matrix has fail-fast: false, so the other architecture may still complete and publish.

The required image job checks the result of both matrix entries. On a push to main, image-index then combines their digests and publishes the multi-platform edge and sha-<commit> tags. Neither tag is a per-architecture tag. The separate empty-world job depends on the build and does not publish an image or gate platform publication.

The rehearsal on each architecture

1. Build and inspect. The content check verifies the platform and native runner, user 10001, Debian 13, Temurin 25, required distribution files, writable paths, and the absence of removed libraries. It checks DatapackRoot = /opt/l2jfree and CatalogDirectory = /opt/l2jfree/catalog, and requires startup to refuse a missing L2JFREE_DB_URL. A separate distribution scan rejects forbidden paths and content, including archive entries. These checks do not compare the whole datapack byte for byte with the repository.

Trivy reports fixed critical and high vulnerabilities here without blocking the merge; a scanner error is also non-blocking in this job. The versioned release and daily scan enforce the policy in SECURITY.md.

2. Start it as an operator would. Run docker compose up -d --wait with the deployment Compose file. A probe sends the first login-protocol packet to port 2106 and connects to port 7777.

3. Complete one client session. The Java smoke client logs in, selects the server, creates a character, enters the world, and logs out. Later steps reuse this account and password.

4. Complete 24 sessions, six at a time. Each client has its own account. Concurrent account, character, and object-id allocation can expose races. This is a correctness scenario, not a capacity measurement or a combat test.

The clients share the Docker gateway address. Before starting the stack, the job raises the connection-accept limits through the operator configuration, so that the address limit does not reject the intended concurrency.

5. Probe database boundaries. The login role can read login.account and cannot read world.player or catalog.npc_template. The world role can read the latter two and cannot read login.account. Neither role is a superuser or can create a schema or extension. These are selected probes, not an enumeration of every grant or a check of the report schema.

6. Read the startup log. The script summary must report at least 400 loaded scripts and zero failed scripts. Explicit script-loading failures, ERROR lines, and uncaught thread exceptions fail the job. WARN lines are printed for inspection and do not fail this log check. Both network ports must report epoll.

The transport check catches a quiet failure mode: Netty's native library needs an executable unpack directory. With an unsuitable tmpfs it had fallen back to Java NIO. The image now supplies a suitable directory, and a selected native transport that cannot load stops startup.

7. Change the operator configuration. The job writes MaximumOnlineUsers = 50 and an unknown GuideProbe key through the guide's printf | docker compose exec -T server tee command. After restart, a warning naming that key proves that the server read the operator file.

8. Restart and find the character. The first account must find exactly one character. The next session creates a second character; a new account is also checked after restart.

9. Check recording and diagnostics. Java Flight Recorder must have non-empty chunks in the log volume. The incident script collects logs, slow statements, database sessions, and a thread dump, and the stack must still serve afterwards.

10. Stop cleanly. The server must save and stop within Docker's grace period, without a forced kill. Compose allows 60 seconds because the save visits players sequentially.

11. Back up and restore. The guide's dump must contain accounts and players and omit the catalog supplied by the image. The job destroys the stack and its volumes, starts a clean stack, confirms the account is absent, restores the dump, and starts again. The original account must find its two characters, and the role probes run again.

12. Rehearse an update when edge exists. The job pulls the published edge image, starts it, and creates an account and character. It replaces that image with the candidate on the same volumes and requires the account and character to survive the migrations.

If edge cannot be pulled, this step records not-rehearsed, emits a warning, and returns success. The first push can therefore publish without proving an update. Once edge is available, rerun both image jobs before a versioned release. A completed rehearsal writes the exact commit SHA to update-rehearsal-amd64 or update-rehearsal-arm64; release verification requires both files to equal that commit.

13. Publish platform digests, then the index. On a push to main, each successful architecture publishes its image by digest, signs its runtime manifest, and attaches provenance. After both succeed, the index job assigns edge and sha-<commit>, signs and attests the index, and verifies the index and both platforms. Publication is a sequence: a later failure can leave an already-published object. A versioned release additionally requires a successful complete build run and the two completed update proofs.

An empty catalog is a separate fixture

The amd64-only empty-world job builds the same distribution into an image. It provides an existing data directory, an empty catalog directory, and a passport containing world.id=empty and world.version=0. The log must contain exactly one empty-world passport with a catalog revision, report readiness, and contain no ERROR, WARN, or stack trace. Both TCP ports must accept a connection. This checks the empty-content startup path, not a playable game.

The negative case points CatalogDirectory at a directory that does not exist. Startup must stop and name both the configuration key and the missing path. An empty directory and an absent directory are different states. This job remains active in 3.3.0; its stricter WARN rule does not apply to the normal image log check.

What the evidence establishes

Each successful rehearsal records specific sessions and recovery operations on the delivered system. It does not prove every quest or combat mechanic, establish capacity, or certify every datapack file. The release workflow consumes the successful run and update proofs before promoting a version.
